# Lean port of CompCert (`export/CCLib`): gap analysis

Scope: the Lean 4 port in `export/` (`CCLib/`, `Clightdefs.lean`, `examples/`)
compared with the Rocq sources in this tree (`lib/`, `common/`, `cfrontend/`,
`aarch64/`). Measured against CompCert 3.17 (`VERSION`).

## Status update (fixes applied)

The following items from this report have since been fixed:

* **§1, all three float bugs.** `CCLib/lib/Floats.lean` now computes every
  float↔integer conversion and `neg`/`abs` exactly from the bit pattern
  (new namespace `Floats.IEEE`: `truncBits`/`truncBitsRange` = Flocq's
  `ZofB`/`ZofB_range`, `ofIntBits` = `BofZ`, single rounding, ties to even).
  `toLong 2^63`, `toLong 1e30`, `toLongu 1e30` are `none`; `toLongu 1e19` is
  `10^19`; `Float32.ofLong (2^62+2^38+1)` is `2^62+2^39`; `abs (-0.0)` is
  `+0.0`; and `Cop.semCast (Vfloat 1e30) tdouble tlong m = none`, so `(long)1e30`
  is stuck as in CompCert. These are proved by `decide` in
  `export/examples/FloatConvCheck.lean` (part of the default build). In ad-hoc
  host testing (not part of the build), 200,000 random cases agreed with the
  hardware conversions wherever those are exact.
* **§0, root `lakefile.toml`.** It now declares `CCLib` and `Clightdefs` with
  `srcDir = "export"` and `Examples` with `srcDir = "export/examples"`, plus the
  `test` and `main` libraries. `lake build` from the repository root (Lean
  4.28.0) builds all of it (78 jobs). Two small compatibility edits were needed
  for the older toolchain: `CC.identOfString_eq_foldr` (`CCLib/lib/Positive.lean`)
  now has a fallback proof used when core lacks
  `String.foldr_eq_foldr_toList`, and two `rw`s in `examples/SepCheck.lean`
  first beta-reduce. `cd export && lake build` (Lean 4.32.1) still builds.
* **§4, documentation.** Line count and test count in `export/README.md`,
  the `bv_decide` remark in `CCLib/lib/Integers.lean`, the opacity and NaN-knob
  remarks in `CCLib/aarch64/Archi.lean`, the "integer-only" remark in
  `CCLib/lib/Floats.lean`, and the Mathlib note in `LEAN.md` are corrected. The
  version (3.17 in `VERSION`, 3.18 in `README.md`/`LEAN.md`/`Changelog.md`)
  is left as is, since the intended version cannot be determined from the tree.

Everything in §2 and §3 (the unported files and theorems) is still open.

**Fidelity fix: `Mem.loadv` / `Mem.storev`.** In this CompCert version
(`common/Memory.v`), `loadv`/`storev` fail when
`Ptrofs.unsigned ofs + size_chunk chunk > Ptrofs.modulus`. The Lean versions
lacked this check, so on a block larger than 2^64 bytes the Lean Clight
semantics could load or store a `double` at offset `2^64 - 4` where CompCert is
stuck. Both now perform the check. Consequences:

* `Mem.loadv_ptr`/`Mem.storev_ptr` (`MemoryTheory.lean`) now need a
  `ChunkNoWrap chunk ofs` argument. It holds automatically (`Or.inl rfl`) for
  every chunk whose alignment equals its size, i.e. all except
  `Mfloat64`/`Many64`, because an aligned in-range access cannot wrap.
* The separation-logic rules that read or write through a pointer
  (`Sep.eval_deref_mapsto`, `eval_field_scalar`, `eval_field_union`,
  `triple_assign`, `triple_assign_any`) take that argument as a trailing
  auto-parameter. None of the existing examples needed changes except the
  chunk-generic `write_field` in `examples/StructCopySep.lean`, which now
  passes the argument on.
* `examples/LoadvWrapCheck.lean` builds a 2^64+8-byte block and proves that the
  raw `load` of a `double` at `2^64 - 4` succeeds, while `loadv`/`storev` through
  the pointer are `none`.

## Status update 5 (float implementation refactored)

`CCLib/lib/Floats.lean` was restructured; the semantics is unchanged.

* **One generic implementation.** Every operation is now defined once in
  namespace `Floats.Gen`, on `BitVec spec.numBits` for an IEEE `Format`, with a
  `Gen.NanConfig spec` for the target's `default_nan`/`choose_nan`. `Float` and
  `Float32` are one-line wrappers instantiating it with
  `Format.binary64`/`binary32` and the `Archi` `_64`/`_32` NaN settings.
  Before, the NaN functions, arithmetic and comparisons were written out twice.
* **Conversions reuse the IEEE model.** The hand-written bit decoding and
  rounding of the old `Floats.IEEE` namespace (`truncBits`, `truncBitsRange`,
  `ofIntBits`) is gone. `Gen.toZ` (Flocq's `ZofB`) reads the value off the
  model's `unpack`. `Gen.toZRange` (`ZofB_range`) is core's `Option.filter`.
  `Gen.ofZ` (`BofZ`) is the model's `normalize` followed by `pack`, the same
  rounding code that `add`/`mul`/… use.
* **Sign operations** use core's `BitVec.twoPow` for the sign bit
  (`Gen.neg`, `Gen.abs`).
* **Lemmas proved once.** `FloatsLemmas.lean` proves `cmp_swap`,
  `add_commut`, `mul_commut`, `to_int_to_long`/`to_intu_to_longu`/
  `to_intu_to_long`, `neg_neg`/`abs_neg`/`abs_abs` in `Gen`, and restates
  them for `Float` and `Float32` in one line each. The `of_*` lemmas reduce to
  five integer facts (`signed_int_long`, …) that are shared by both formats.
  Core's `Option.map_eq_some_iff` and `Option.filter_eq_some_iff` replace a
  local copy and a hand proof.
* **Not changed:** the CompCert-facing names and statements, the
  `toNative`/`ofNative` printing bridges, and `CCLib/lib/FloatModel.lean`. The
  backport stays because Lean v4.32.1 has no `Float.Model`. On a toolchain
  that ships it (v4.33.0 or later) the file can be replaced by core's
  `Float.Model` (only the namespace differs). Lean's built-in `Float`/`Float32`
  cannot replace the model: on v4.32.1 their operations are opaque `@[extern]`
  constants, so they cannot be reasoned about or evaluated in the kernel, and
  their NaN payloads come from the host FPU rather than CompCert's `Archi`
  rules.
* **Checking:** `lake build` succeeds (117 jobs, no `sorry`). All
  `decide`-checked cases in `examples/FloatConvCheck.lean` still pass,
  including single rounding of `int64 → float32`, ties to even, and range
  failures. An ad-hoc comparison of the old and new conversion and sign code
  on 200,000 random inputs per function found no difference. That comparison
  is not part of the build.

8-byte pointers. `transfRtlProgram` and `transfCminorProgram` are the ARM /

**Why the remaining ARM/PowerPC proofs are not ported.** `Selectionproof`,
`RTLtyping`'s subject reduction (and with it `Allocproof`), `Stackingproof`
and `Asmgenproof` rely on facts that are **false** over the port's 64-bit value
layer (`Archi.ptr64 = true`). `examples/ArmPpcPtr64Gap.lean` proves this:
* `arm_type_of_operation_sound_fails`, `powerpc_type_of_operation_sound_fails`:
  `Op.type_of_operation_sound` fails for `Oaddrstack`. The result type is
  `Tint`, but the result is a pointer, and with 64-bit pointers a pointer
  does not have type `Tint` (`vptr_not_tint`). So well-typed register states
  are not preserved, and `RTLtyping.subject_reduction` cannot hold.
* `arm_aindexed_zero_ptr`, `powerpc_aindexed_zero_ptr`: the fall-back
  addressing mode `Aindexed 0` that instruction selection uses for a
  computed pointer evaluates to `Vundef` (`Val.add (Vptr b o) (Vint 0)` is
  `Vundef` when `ptr64 = true`). So `Selectionproof.eval_load`/`eval_store`
  are false: the selected load is stuck where the Cminor load succeeds.
  The same issue affects `Stackingproof` (stack slots of type `Tint` drop
  pointers via `Val.load_result Mint32`, `arm_locmap_set_tint_ptr`) and
  `Asmgenproof`.

`round a ≤ r ≤ round b` for all `a, b ≥ 0` with `a * a ≤ x ≤ b * b`. These
hold for `round (sqrt x)` with any rounding function. For the IEEE rounding
modes they determine `r` (an irrational `√x` lies strictly between two
consecutive rational break points of the rounding). That uniqueness is
argued informally, not proved in Lean. The proof of `Bsqrt_correct_aux` differs from
Rocq's: it applies `binary_round_aux_correct'` to a rational with the same
position as `√x` between two consecutive floats, and it rules out overflow
directly instead of through a relative-error bound.

The `cmp_of_comparison_*` lemmas listed as missing in Status update 50 were
already ported (`lib/FloatsLemmas.lean`, as `cmpOfComparison_*`).

**Still not ported:** the `Double_round_sqrt*` sections of
`flocq/Prop/Double_rounding.v`, because their statements compose two
roundings of `sqrt x`; the ARM/PowerPC proofs blocked as explained in Status
update 47; and `*/extractionMachdep.v`, which is OCaml only.

## Status update 57 (PowerPC `LinkerParams` had no inhabitant; PowerPC `transl_op_correct`)

**Fidelity bug fixed: the PowerPC linker parameters were uninhabited.**
`powerpc/Asm.lean` turns the Rocq parameters and axioms of `powerpc/Asm.v`
about symbol resolution into the fields of a structure `LinkerParams`. One of
those fields was the Rocq axiom `low_high_half`:
`Val.add (high_half ge id ofs) (low_half ge id ofs) = Genv.symbol_address ge id ofs`
for every global environment. In the port's 64-bit value layer
(`Archi.ptr64 = true`), `Val.add` never returns a pointer, but the address of
a defined symbol is a pointer. So no value of type `LinkerParams` could exist.
As a result, every PowerPC result that takes the linker parameters as an
argument (the `Asm` semantics and its determinacy, `Asmgenproof0`,
`Asmgenproof1*`, `Asmgenproof`) was vacuously true, and the PowerPC compiler
`Config` could not be built. `examples/PowerPCLinkerParams.lean` (in the
default build) proves both halves:
* `rocq_low_high_half_unsat`: the unguarded equation has no solution;
* `linkerParams_inhabited`: the corrected structure has an inhabitant.

The fix adds the hypothesis `Archi.ptr64 = false` to the field
`low_high_half`, which is what Rocq assumes for PowerPC. No existing proof
used the field, so all of them still build, and they are no longer vacuous.

**Newly ported.**

| Rocq source | Lean file | Content |
|---|---|---|
| `powerpc/Asmgenproof1.v` | `powerpc/Asmgenproof1Op.lean` (new) | `transl_op_correct_aux`, `transl_op_correct` |

Difference from Rocq: both theorems assume that the operation is neither
`Oaddrsymbol` nor `Oaddrstack`, as ARM's `transl_op_correct` does for
`Oaddrstack` (Status update 56). The code generated for these two operations

## 1. Fidelity bugs found (reproducers: `export/examples/FloatConvGaps.lean`)

These are differences from CompCert's specification, not gaps in coverage.
All of them are in `CCLib/lib/Floats.lean`, and the differential corpus does not
catch them.

| # | Function(s) | CompCert (`lib/Floats.v`) | Port | Effect |
|---|---|---|---|---|
| 1 | `Float.toLong`, `Float.toLongu`, `Float32.toLong`, `Float32.toLongu` | `None` when the truncated value is out of range | it computes `x.toInt64` (which **saturates**) and then range-checks the saturated value | `toLong 2^63`, `toLong 1e30`, `toLongu 1e30` return `some 0x7fff…ffff` where CompCert gives `none`. `toLongu 1e19` returns `2^63-1` where CompCert gives `10^19` |
| 2 | `Float32.ofLong`, `Float32.ofLongu` | one rounding, straight to binary32 (`BofZ 24 128`) | rounds to binary64 first, then to binary32 (two roundings) | `ofLong (2^62+2^38+1)` gives `2^62`; CompCert gives `2^62+2^39` |
| 3 | `Float.abs`, `Float32.abs` | `Babs`, which clears the sign bit | `if x < 0 then -x else x` | `abs(-0.0) = -0.0` where CompCert gives `+0.0` |

Bug 1 reaches the semantics: `Cop.semCast (Vfloat 1e30) tdouble tlong m`
returns `some (Vlong LLONG_MAX)`, so the Lean Clight `Step` takes a step on
`(long)1e30`. In CompCert that conversion is undefined behaviour and the
program is stuck. Because the program logic gives total correctness, a Lean
proof could show such a program "safe" when CompCert considers it undefined.
This is the only soundness-relevant difference from CompCert that I found.

Suggested fixes: range-check the *real* value before converting (for example
`lo ≤ x.floor`-style checks against exact powers of two, or decode the bits
yourself); for int64 → binary32, round from the integer directly (split the
integer, or implement round-to-odd followed by a single rounding); for `abs`,
clear bit 63 or bit 31 of the bit pattern.

## 5. Suggested priorities

1. Fix the three float bugs in §1, and add out-of-range and edge cases to the
   differential suite.
2. Repair or remove the root `lakefile.toml` so the port builds from the
   repository root (for example: one `CCLib` library with `srcDir = "export"`).
3. Port the theorem layers most needed for verification work: `Maps` (`gss`,
   `gempty`, remove, `elements`), the general `Memory` load/store/alloc/free
   algebra, and the `Integers` `repr`/`unsigned`/`signed` lemmas.
4. Port `Builtins0/1` so the common builtins get semantics.
5. Port `Smallstep.semantics`, `forever` and `Behaviors` to support
   divergence and "goes wrong"; then `Ctyping`.
6. If proofs about float arithmetic are wanted, replace the host-`Float`
   substitution with a kernel-reducible IEEE model (a Flocq-style port, or a
   bit-level softfloat proved against a real-number spec).
